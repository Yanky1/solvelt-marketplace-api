| M1-09 | 2026-11-04 | Retry policy (replaced after orchestrator review of 2a): network errors, per-attempt timeouts (<= 30 s, `Portal:AttemptTimeoutSeconds`), `503` and `409` with `code` `concurrent_update`/`version_conflict` are retried (max `Portal:MaxAttempts`, default 5; backoff jittered exponential from `Portal:RetryBaseDelayMs`, capped 30 s; `Retry-After` honoured, capped 30 s). For `payment-events` additionally `404 order_not_found/booking_not_found` and `409 sale_not_recorded` (not retried for any other call). Never retried: `401`, `413`, `422`, every other 4xx, and **`429`**: the portal's limiter is a fixed one-minute window without `Retry-After`, so short backoffs only add load; a 429 is returned with `Retryable = true` for the outbox to retry later. A `503` **without** `Retry-After` is read as "busy": it is retried with our own backoff, inside the total deadline (M1-19). Exhausted network errors throw `PortalUnavailableException`; a retryable HTTP answer that is still the last one is returned with `Retryable = true`. | Every write carries our own idempotency id, so retries are safe. |

| M1-13 | 2026-11-04 | **Logging (orchestrator review 1.1, extended).** `appsettings.json` sets `Microsoft.AspNetCore` and `System.Net.Http.HttpClient` and `Microsoft.EntityFrameworkCore` to Warning and `Microsoft.AspNetCore.Hosting.Diagnostics` to **None**. Warning alone is not enough: the hosting diagnostics logger also attaches a `RequestPath:` logging **scope** (full path, so `/verify/<email>/<token>`) to every log line written during a request, including our own, and scope-aware providers (JSON, OTel, App Insights) would record it; the scope is only created while that category is enabled. A test captures every log line including scopes through a fake `ILoggerProvider` and asserts that an email, a token in the path, a token in the query and a posted password never appear; it fails if the category goes back to Warning or the section is removed. `Microsoft.AspNetCore: Warning` itself is defence in depth and is not pinned by a test. | Tokens and emails appear in URLs. |
| M1-14 | 2026-11-04 | **Per end-user rate limits (review 1.3).** Every buyer request arrives from the web server (O-02), so the socket address cannot key a limit. The web server forwards the end-user IP in `X-Solvelt-Client-Ip`, `X-Solvelt-Client-Timestamp` (unix seconds, +-300 s) and `X-Solvelt-Client-Signature: v1=hex HMAC-SHA256(Web:ForwardingKey, "<timestamp>\n<ip>")`. `Web:ForwardingKey` is its own key (env `Web__ForwardingKey`, >= 32 chars, required in Production, must differ from both portal secrets); a dedicated signed header was chosen over `ForwardedHeaders`/`KnownProxies` because the web tier's addresses are not fixed. A missing, malformed, stale or wrongly signed set is ignored and the request is keyed by the socket address (`peer:`), so a client cannot pick or rotate its bucket; a null remote address maps to `peer:unknown` instead of throwing. IPv6 collapses to its /64 and IPv4-mapped IPv6 to IPv4. Buckets are per (policy, end user), so `auth` and `public` never share. Documented in `docs/API.md` for W1. | Review hotspot: one abuser must not lock everyone out. |

It is wired into sign-in, reset and verification in the auth slice together with durable lockout in the database. | Review 1.3: "also key auth endpoints by account or email". |

| M1-19 | 2026-11-04 | **Total deadline (review 2a.1, orchestrator decision O-08).** One deadline covers all attempts and backoffs of a call: `Portal:TotalDeadlineSeconds`, default 30, clamped to 1..60. An attempt is bounded by `min(Portal:AttemptTimeoutSeconds (clamped 1..30), time left)`; the next attempt starts only if its backoff still fits (`elapsed + backoff < total`), otherwise the last answer is returned (`Retryable`) or `PortalUnavailableException` is thrown. Longer persistence is the outbox's job (ingest and payment events go through our outbox with its own backoff). Timers run on the injected `TimeProvider` (`new CancellationTokenSource(timeout, time)`), so tests drive them with a `FakeTimeProvider` against a portal that never answers. | A caller (checkout, a worker) must not block for ~270 s. |
| M1-20 | 2026-11-04 | `Retry-After` is read as delta seconds or as an HTTP date (date minus now, floor 0), capped at 30 s. An oversized portal response (> 2 MB) throws `PortalResponseTooLargeException` and is **not** retried (the write may already be applied; the outbox re-sends with the same idempotency id). `Portal:BaseUrl` is validated at start-up outside Dev/Testing (absolute `https`, no credentials, no path, no query or fragment) and by the client registration in every environment (`http(s)`, no path/query). Bodies are exactly capped at 262144 bytes (262145 refused). System.Text.Json escapes non-ASCII as `\uXXXX`, so signed bodies are pure ASCII. | Review 2a items 5, 6, 7. |
| M1-21 | 2026-11-04 | `FakePortal` reads `RequestUri.PathAndQuery`; the real portal reads Kestrel's `GetEncodedPathAndQuery`.
