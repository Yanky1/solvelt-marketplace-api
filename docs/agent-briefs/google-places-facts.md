# Google Maps facts for the street search and the ZIP check (decision V-63)

Read by the orchestrator on 2026-11-26 from developers.google.com and passed to the voice worker in cross-session messages; copied here with the sources the orchestrator named. Anything marked **NOT STATED** is not in the code, or is behind an owner decision. Places API (Legacy) "can no longer be enabled for new Google Cloud projects" (as of October 2026): only Places API (New) is used, together with the Geocoding API.

## Geocoding API (ZIP code to city, state and viewport)
Source: developers.google.com/maps/documentation/geocoding/requests-geocoding (v3, current; the overview also says "Version 4 ... is generally available").
- `GET https://maps.googleapis.com/maps/api/geocode/json?address=ZIP&components=country:US&key=KEY`. HTTPS is required and "all reserved characters ... must be URL-encoded". Do not repeat component filters (country, postal_code, route): INVALID_REQUEST.
- **THE KEY IS IN THE URL.** The URL, the request and any exception whose message may carry it are never logged; only the HTTP status is. A test checks that the key never appears in a captured log or exception.
- Response: `results[0].address_components[] { long_name, short_name, types[] }`: city = `locality`, else `postal_town`, else `sublocality` (long_name); state = `administrative_area_level_1` (short_name). `results[0].geometry.viewport { northeast {lat, lng}, southwest {lat, lng} }`.
- `status`: `OK` and `ZERO_RESULTS` (a real answer: no such ZIP) are answers; `OVER_DAILY_LIMIT`, `OVER_QUERY_LIMIT`, `REQUEST_DENIED`, `INVALID_REQUEST`, `UNKNOWN_ERROR` mean "unavailable", not "bad ZIP". A transport 200 is not success by itself. `error_message` may be present: never logged or spoken.

## Places API (New) Autocomplete (street names)
Sources: developers.google.com/maps/documentation/places/web-service/place-autocomplete and .../place-types.
- `POST https://places.googleapis.com/v1/places:autocomplete`, header `X-Goog-Api-Key` (not in the URL), JSON body. `X-Goog-FieldMask` is optional here.
- Body used: `input` (what the caller said, whole or partial), `includedPrimaryTypes: ["route"]` ("route" is in Table B, and the place-types page says Table B types "are only filterable using includedPrimaryTypes for Place Autocomplete"; it matches the PRIMARY type only; up to five types; INVALID_REQUEST for more than five or an unrecognised one), `includedRegionCodes: ["us"]` (two-character ccTLD codes, up to 15), `languageCode: "en"`, and when the ZIP's viewport is known `locationRestriction: { rectangle: { low: {latitude, longitude} = southwest, high: {latitude, longitude} = northeast } }` (results outside are excluded; "Both low and high must be populated, and the represented box cannot be empty. An empty viewport results in an error"). Never a bias and a restriction together; with neither, Google biases by OUR server's IP, so a region is always sent.
- Response: `suggestions[]` with `placePrediction { place, placeId, text { text }, structuredFormat { mainText { text }, secondaryText { text } }, types[] }` (up to five; `secondaryText` may be missing) or `queryPrediction` (skipped). A street name is `structuredFormat.mainText.text`, else `text.text` up to the first comma; names are de-duplicated without regard to case; at most five.
- **No session token is sent.** There is no Place Details request in this design, so a session would never be terminated; per the session-pricing page "Incomplete sessions ... are billed only for the Autocomplete (New) requests using the SKU: Autocomplete Requests", so a token buys nothing.

## Key and setup
One server-side key with an API restriction to **Geocoding API + Places API (New)** and an application restriction to the server's IP addresses (Google "strongly recommends restricting your API keys"). Never in a web client. A Google Cloud project with billing enabled and both APIs enabled. Setting: `Voice:Google:MapsApiKey` (secret, environment only). EEA billing addresses have different terms: the owner checks. Missing key: the street search and the ZIP check are off with one warning; the offline `check_address` still works.

## Policy
"You must not pre-fetch, cache, or store Places API content beyond the allowed exceptions." Place ids may be stored indefinitely; latitude and longitude may be cached for up to 30 consecutive calendar days, then deleted. Therefore (a deviation from the telephone system's own code, which caches city and state for seven days, made for the terms): the **viewport** (latitude and longitude) is cached in memory for **seven days**; the **city and state** of a ZIP are kept **for one call only**, in that call's memory; no place id, no street name and no address is stored. "When displaying Places API data without a Google Map, you must include the Google logo"; **spoken** use is NOT STATED. The design says never to name a vendor to the caller, so no attribution is spoken: **owner / legal to confirm** (DECISIONS V-63). No map is shown, so the rule about non-Google maps does not apply. The owner's decision (Ronald, relayed by the orchestrator, 2026-11-26) is to build from the telephone system's design and to store the address the CALLER states and confirms: the caller says their own house number and picks a street name from the list. Whether Google's terms allow the street name and the city and state that the caller confirmed after hearing them from these answers to be stored in the order is NOT STATED on the pages read (the Service Specific Terms decide; "consult your legal counsel"): **owner / legal to confirm**, recorded in DECISIONS V-63. Nothing else of Google's answers is kept.
