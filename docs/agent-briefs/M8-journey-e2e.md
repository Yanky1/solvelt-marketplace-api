# Brief M8: buyer-journey E2E against the real seller portal + screenshots
**Depends on:** M3, M5, M6 (and the portal's C1 catalog feed).
Bring up the **real portal backend** (Yanky1/Yanky1-test-login-backend, read-only: build and run it, never change it) in Testing mode with shared
dev secrets, the marketplace API and the web server, all in one CI workflow `journey.yml` (also runnable locally by a script). Stripe in **test mode** with
the fake provider in CI and an opt-in job that uses real Stripe test keys from repository secrets when present (`STRIPE_TEST_SECRET_KEY`; skipped, not failed, when absent; record it).
Journey: a seller (portal API) creates and activates a product → the catalog syncs → buyer browses/searches → adds to cart → pays (3DS test card in the opt-in job) →
the order appears in the seller portal (assert via the portal API) → seller accepts and ships with tracking → buyer sees tracking → delivered → buyer reviews → review visible.
Also a service booking journey (availability → hold → pay → confirmed) and a refund journey (seller refunds → Stripe refund → `refund.processed` reaches the portal ledger).
Screenshots of every buyer page: desktop + mobile, light + dark, in `docs/screenshots/` of the web repo, regenerated by script.

**Portal checkout in CI:** Yanky1/Yanky1-test-login-backend is private (2026-11-04). Check it out with a read-only token secret `BACKEND_REPO_TOKEN`, which only the owner can add. If it's missing, the journey job must **fail with a clear message**: never skip it, never fall back to a mock portal and call it green. Ask the orchestrator to have the owner add it.
