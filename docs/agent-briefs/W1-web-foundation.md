# Brief W1: buyer website foundation

**Repo:** Yanky1/solvelt-marketplace-web. **Branch:** `feat/w1-foundation` (later slices `feat/w1-<slice>`). **Approved assignment** from the repository
owner (see CLAUDE.md): carry it out without asking for confirmation. Record decisions in `docs/DESIGN.md` of the web repo (ids `W1-01`, …).

## Context
Solvelt is a multi-seller marketplace for products and services (kosher-aware). The seller portal exists (read-only for you). The marketplace API
(Yanky1/solvelt-marketplace-api, ASP.NET Core 10) is being built in parallel by the M1 worker; its endpoints are documented in that repo's
`docs/API.md` and decisions in `docs/DECISIONS.md`, and its integration plan in `docs/CONTRACT.md`. You may attach it with `add_repo`
(owner `Yanky1`, repo `solvelt-marketplace-api`, access `read` is enough for you) to read those docs; never change it. If an endpoint you need
isn't merged yet, build against a typed client + MSW handlers shaped like the brief below, and wire it up when it lands.

## Product decisions (owner)
* **React + TypeScript, React Router v7 in framework mode with SSR** (not Next.js). Product, service, brand and category pages must be crawlable.
* **Same Solvelt Figma styling as the seller portal**: Playfair Display (display) + Plus Jakarta Sans (UI), deep green + gold, light and dark.
  Only the styling is shared; the buyer layouts are new. Tokens are in the appendix (copied from the portal's `src/styles.css`); start from them, self-host fonts (`@fontsource/*`).
* Images handled by us: responsive `srcset`/`sizes`, lazy loading, explicit width/height (no layout shift), a resize step on our server.
* Tests: Vitest + React Testing Library + MSW; Playwright E2E with `@axe-core/playwright`.

## Scope of W1
1. **App skeleton:** RR7 framework mode (`react-router.config.ts`, `ssr: true`), Node server, TypeScript strict, oxlint or ESLint, env-based config
   (`API_BASE_URL`, `SESSION_COOKIE_SECRET`), start-up fails in production when required config is missing.
2. **Design system:** tokens from the appendix as CSS custom properties; light/dark with a user choice stored in a **cookie** and applied during SSR
   (no flash of the wrong theme), defaulting to `prefers-color-scheme`. Base components: button, link, input/field with errors, select, checkbox, card,
   badge, price, rating stars (display only), skeletons, toast, modal/drawer, pagination, breadcrumb, empty state. 44 px targets, visible focus rings.
3. **Buyer shell:** header (logo, search box, category menu, account, cart count placeholder), mobile nav drawer, footer, skip link; error and 404 pages.
4. **Auth via BFF** (API decision O-02): the API issues opaque session tokens; the web server stores the token in its own `HttpOnly; Secure; SameSite=Lax`
   cookie and calls the API with `Authorization: Bearer`. The token never reaches browser JS. CSRF protection on every mutating action (Origin check plus a
   per-session token). Pages: sign up, sign in, verify email, forgot/reset password, passkey sign-in and passkey management (`@simplewebauthn/browser`
   or the native WebAuthn API), sign out / sign out everywhere, profile, addresses (CRUD, default). Guest-checkout entry is M3; leave a placeholder.
5. **Catalog pages (basic; search/filters/SEO depth are M2):** home (featured categories and listings), category page, brand page, listing detail
   (product and service variants of the layout), all SSR from the API's `/api/v1/catalog/*`.
6. **SEO scaffolding:** per-route `meta` (title, description, canonical, Open Graph), `robots.txt`, a `sitemap.xml` resource route (catalog-driven), JSON-LD helpers (`Product`, `Offer`, `BreadcrumbList`, `Organization`).
7. **Images:** an `<Img>` component (srcset from an allow-list of widths, `sizes`, `loading="lazy"` except the LCP image, width/height) and a resize route
   `/img/:imageId?w=` using `sharp` (Apache-2.0), allow-listed widths only, WebP/AVIF by `Accept`, long immutable cache headers, size limits. Images come from the API (later from the portal catalog feed).
8. **CI:** `ci.yml` (lint, typecheck, unit tests, build) and `e2e.yml` (Playwright against the built SSR server with a mock API, axe on every page in **light and dark**, desktop and mobile). Both must run on feature-branch pushes and `main`.
9. **Screenshots** desktop + mobile, light + dark, of every W1 page in `docs/screenshots/`, regenerated by a script.
10. **Docs:** README (run, test, config), `docs/DESIGN.md` (decisions, component list, theming).

## Review hotspots (the orchestrator checks these on every merge)
Dark-mode contrast (axe must pass in dark too; check gold-on-green and muted text); session token never in client JS, HTML, logs or `localStorage`;
local/session storage cleared at the right moments (sign-out clears user-scoped data only, theme preference stays); CSRF on every action; no PII in
client logs or URLs; open redirects in `?next=` (allow relative paths only); SSR loaders never leak one user's data into a cached response (`Cache-Control: private` on personalised pages).

## Definition of done
Feature branch rebased on origin/main; **CI and E2E green on that exact commit**; no test skipped or weakened; fast-forward push to main (or
rebase-merge PR if refused). Small slices welcome: skeleton + tokens + CI first, then auth, then catalog pages.
