Short names used below: **Realtime** = the `/v1/realtime` API with `gpt-realtime-2.1` and `gpt-realtime-2.1-mini` (what we run, `Voice:OpenAiModel`, `Voice:OpenAiModelMini`); **GPT-Live** = the `/v1/live/sessions` API with `gpt-live-1`.

## 1. Models, prices and cost per call-minute

| | Realtime (ours today) | GPT-Live |
|---|---|---|
| Model ids | `gpt-realtime-2.1` and `gpt-realtime-2.1-mini` (the endpoint `v1/realtime` is the only one that supports them) | `gpt-live-1` (the endpoint `v1/live/sessions` is the only one that supports it; `v1/realtime` is "Not supported") |
| Billing | per token | **$0.05 per minute of voice session, billed per second**, not rounded up; "Backend model and tool usage is billed separately" |
| Sources | https://developers.openai.com/api/docs/models/gpt-realtime-2.1 , https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini | https://developers.openai.com/api/docs/models/gpt-live-1 , https://developers.openai.com/api/docs/pricing |

Realtime prices per 1M tokens (same pages as above and the pricing page): `gpt-realtime-2.1` audio in $32, audio out $64, cached audio in $0.40, text in $4, text out $24, cached text in $0.40; `gpt-realtime-2.1-mini` audio in $10, audio out $20, cached audio in $0.30, text in $0.60, text out $2.40, cached text in $0.06. These equal the prices already in our configuration (`VoiceOptions.PricePerMillionFull` and `PricePerMillionMini`, `src/Solvelt.Marketplace.Api/Voice/VoiceOptions.cs`, and `docs/VOICE.md` section 3).

What counts as GPT-Live session time: "Active session time includes time when the user speaks, the assistant speaks, both are silent, or the backend is working", counted "from start through closure" (https://developers.openai.com/api/docs/guides/voice-latency-cost). So a caller who is silent or waiting on a tool is billed at the same rate. For WebRTC sessions only, creating the session bills 15 seconds up front, credited against the duration (same page); the page says nothing about WebSocket or SIP initialisation, so that is OPEN (we would use WebSocket, see section 3).

**Token conversion used for Realtime** (OpenAI): "Audio tokens in user messages are 1 token per 100 ms of audio, while audio tokens in assistant messages are 1 token per 50ms" (same cost page). So the caller's audio, streamed all call long, is about 600 tokens per call-minute, and the assistant's speech is about 1,200 tokens per minute it speaks.

**Assumptions (mine, unmeasured, replace with the staff report's measured `costPerMinute`):** caller audio streamed the whole call; the assistant speaks 25%, 50% or 70% of the call; audio tokens only. Not included: text tokens (instructions, tool definitions, history re-read on each response, cached at the cached-input prices above), SignalWire voice and SMS charges (the same for both), and the 15-minute call cap (`Voice:MaxCallSeconds` 900).

| Per call-minute, audio only | assistant speaks 25% | 50% | 70% |
|---|---|---|---|
| Realtime full (`gpt-realtime-2.1`): 600 x $32/M + (1,200 x share) x $64/M | $0.038 | $0.058 | $0.073 |
| Realtime mini (`gpt-realtime-2.1-mini`): 600 x $10/M + (1,200 x share) x $20/M | $0.012 | $0.018 | $0.023 |
| GPT-Live voice session alone | $0.050 | $0.050 | $0.050 |

GPT-Live also needs a backend, billed on top (https://developers.openai.com/api/docs/guides/voice-latency-cost). An **illustration** with assumed backend usage of one delegated request per call-minute, 4,000 input tokens (none cached) and 150 output tokens, at the short-context prices on https://developers.openai.com/api/docs/pricing: `gpt-6-luna` ($0.10 in, $0.50 out per 1M) adds about $0.0005 per call-minute, `gpt-6.1-terra` ($1 / $5) about $0.0048, `gpt-6.1-sol` ($2 / $10) about $0.0095. The real number depends on how often our tools run and on the backend we choose: OPEN until measured.

**Our real configuration split:** the code defaults are `ModelMode = full`, `MiniPercent = 50` (used only in `split`), `OpenAiVoice = cedar`, `TurnDetection = semantic_vad`, `MaxCallSeconds = 900` (`VoiceOptions.cs`). The deployed values live in the host's secret store, not in the repository, so the deployed split is OPEN. At `full` the audio-only figure is $0.038 to $0.073; at `split` with 50% mini it is the average of the two Realtime rows ($0.025 to $0.048). **GPT-Live's voice session alone ($0.05) is inside the range of Realtime full and above mini, and the backend comes on top, so on price GPT-Live is not cheaper than our mini tier; any case for it would have to be about quality.**

## 2. Latency, voice quality and voices

- **Latency:** the developer pages I could read publish **no latency figures** for either API (searched the model pages, the voice-agents, latency/cost, live and Realtime guides): OPEN. What they say: GPT-Live "can listen and speak at the same time", with reasoning and tools in a separate backend while "users can keep talking while backend work runs" (https://developers.openai.com/api/docs/guides/voice-agents); backend latency is added by the backend and has its own guidance, including `delegation.responses.service_tier: "priority"` for Fast mode (https://developers.openai.com/api/docs/guides/live-delegation); `gpt-realtime-2.1` "updates GPT-Realtime-2 with improved alphanumeric recognition, silence and noise handling, and interruption behavior" and has configurable reasoning effort, where "Higher reasoning effort can increase latency" (https://developers.openai.com/api/docs/models/gpt-realtime-2.1). Measuring audible response time on our line is the only way to compare: https://developers.openai.com/api/docs/guides/voice-agents#measure-latency says to track the median and the 95th percentile.
- **Voice quality:** OpenAI describes `gpt-live-1` as its "premier model for natural, expressive voice conversations with smooth interruption handling" (model page above). No quality benchmark is published on the pages read: OPEN; judging it is a listening test (we already have `tools/voice-samples`).
- **Voices, Realtime:** `alloy`, `ash`, `ballad`, `coral`, `echo`, `sage`, `shimmer`, `verse`, `marin`, `cedar` (https://developers.openai.com/api/docs/guides/realtime-conversations). Ours is `cedar`.
- **Voices, GPT-Live:** default `marin`; "these additional voice options": quartz, ripple, vesper, willow, stone, gleam, meridian, bossa, tempo, beacon, delta, cinder (English variants and Brazilian Portuguese), nuri, juni, flitz (German), brise, sillage (French), nira (Hindi), harema, shida (Japanese), noeul (Korean) (https://developers.openai.com/api/docs/guides/live-conversations). The page lists no Hebrew voice. Whether `cedar` (ours) exists on GPT-Live is **OPEN** (the page lists only the additional voices). Custom voices: a voice can be made from a text description for GPT-Live only (free to create, "billed at regular session rates" when used) and "aren't supported by the Text to Speech, Realtime, or Chat Completions APIs"; a voice from a recording is limited to eligible customers (https://developers.openai.com/api/docs/guides/custom-voices).

## 3. SignalWire connectivity

- **What we do today:** SignalWire `<Connect><Stream>` to our WebSocket; our `RealtimeBridge` relays PCMU 8 kHz both ways and talks to `/v1/realtime` with `audio/pcmu` in and out (`src/Solvelt.Marketplace.Api/Voice/RealtimeBridge.cs`, session setup at the `session.update`).
- **SignalWire side:** a bidirectional Stream's default codec is `PCMU@8000h`, also `L16` at 16 or 24 kHz; the stream can send a **mark** ("Request playback completion acknowledgment") and a **clear** ("Flush the audio buffer"); the stream goes to a WebSocket server you run (https://developer.signalwire.com/compatibility-api/cxml/voice/stream/).
- **GPT-Live side, WebSocket:** `session.audio.format` can be `audio/pcm` at 24 kHz (default) or 16 kHz, **`audio/pcmu` at 8 kHz (G.711 mu-law)** or `audio/pcma` at 8 kHz; "A matching G.711 stream can pass through without conversion to PCM" (https://developers.openai.com/api/docs/guides/voice-websockets). So **SignalWire's mu-law 8 kHz can be passed to GPT-Live without transcoding, but through our own server**: SignalWire only talks to a WebSocket we run, and OpenAI documents no SignalWire endpoint. **We keep a bridge** (a `GPT-Live` counterpart of `RealtimeBridge`).
- **Partners and SIP:** OpenAI's partner guides are LiveKit, Twilio, Telnyx, Bandwidth and Daily/Pipecat; SignalWire is not listed (https://developers.openai.com/api/docs/guides/live-partner-integrations). OpenAI's SIP route: a trunk to `sip:$PROJECT_ID@sip.api.openai.com;transport=tls` (EU `sip-eu.api.openai.com`), "GPT-Live requires SRTP for call audio", webhook `live.transport.incoming`, and "Confirm that GPT-Live SIP support is enabled for your project" (https://developers.openai.com/api/docs/guides/voice-sip). SignalWire documents SIP gateways that forward calls to external SIP addresses "with support for configurable encryption and codec settings" and keep a URI that has a user part unchanged (https://signalwire.com/docs/platform/voice/sip). **Neither vendor documents SignalWire to GPT-Live; whether it would work is OPEN and untested.** My inference, not documented: a SIP hand-off would take the call out of our cXML call flow (the keypad `<Gather>`, `<Pay>` and server-spoken steps), which is why the stream bridge is the natural route.

## 4. Barge-in (V-12)

- **Realtime on a WebSocket (ours):** the application must tell the model how much was heard: OpenAI says that in "WebRTC and SIP connections the server manages a buffer of output audio ... and will automatically truncate unplayed audio when there's a user interruption", and for other connections you send `conversation.item.truncate` with the played duration as `audio_end_ms`; with VAD an interruption cancels the response (`response.done` with status `cancelled`) (https://developers.openai.com/api/docs/guides/realtime-conversations). That is what V-12 does (mark echoes -> played milliseconds -> `clear` to the phone, `truncate` and `response.cancel` to the model; `RealtimeBridge.cs`, `VoicePlayback.cs`).
- **GPT-Live:** the model "can listen and speak at the same time, respond to interruptions" and its prompt template has an `Interruption policy` (https://developers.openai.com/api/docs/guides/live-prompting). On the primary WebSocket, "`session.output_audio.delta` events have no timing fields or output-audio-done event" and "Track playback with your application's audio queue" (https://developers.openai.com/api/docs/guides/live-conversations , https://developers.openai.com/api/docs/guides/voice-websockets); migrating from Realtime, "GPT-Live has no equivalent event for the end of each spoken response" (https://developers.openai.com/api/docs/guides/live-migration). To block audio, "control playback at the client or media relay ... discard locally queued audio" (https://developers.openai.com/api/docs/guides/voice-server-controls). **So the phone-side mark/clear logic stays with us.** The Live guides I read document **no `truncate` or `cancel` client event**; how GPT-Live learns what the caller actually heard when audio is queued on a phone line is **OPEN** (needs a spike). Stopping speech "leaves backend work running": the application decides to finish or cancel it (https://developers.openai.com/api/docs/guides/live-migration).

## 5. Turn detection

- **Realtime:** `server_vad` (`threshold`, `prefix_padding_ms`, `silence_duration_ms`) and `semantic_vad`, set with `session.audio.input.turn_detection` (https://developers.openai.com/api/docs/guides/realtime-vad); we default to `semantic_vad`.
- **GPT-Live:** the migration table says to "Stream audio continuously. GPT-Live decides when to speak; remove manual audio commits and voice-turn triggers", and input can be muted or unmuted (https://developers.openai.com/api/docs/guides/live-migration , https://developers.openai.com/api/docs/guides/voice-websockets). **No turn-detection setting (no `semantic_vad`, `server_vad`, threshold or silence option) appears in any GPT-Live guide I read** (searched all of them): OPEN whether it can be tuned; turn-taking is steered with the Live prompt's backchannel and interruption policies. `Voice:TurnDetection` would have no counterpart.

## 6. Tool calling, instructions and platform-spoken lines

- **Architecture:** with Realtime one model hears, decides and calls our function tools (`function_call` items; our bridge returns `function_call_output`; `RealtimeBridge.cs`). With GPT-Live the voice model "delegates reasoning and tool use to a separate backend": either **Responses delegation** (an OpenAI-hosted Responses model picks tools; "Your application still runs custom functions") or **client delegation** (our own agent or workflow); "Keep detailed instructions, business rules, and tool workflows here" in the backend, and conversation style and when to delegate in the Live prompt (https://developers.openai.com/api/docs/guides/live , https://developers.openai.com/api/docs/guides/live-delegation). The `gpt-live-1` page lists `function_calling` and `streaming` as supported features (model page above).
- **So the answer is "no, not unchanged":** our tools (`ToolKit` definitions, `VoiceTools.cs` and the per-area tool classes) keep their server logic and permission checks but are called from the backend path, not by the voice model; the instructions (including the V-11 Scope block) must be **split** into a short Live prompt and a backend prompt, and OpenAI says to keep "safety and privacy limits in both prompts wherever they affect what that model may say, ask, or do" (https://developers.openai.com/api/docs/guides/live-migration). The `off_topic` tool and strike limit (V-11, `VoiceTopic.cs`) become a backend tool, or logic on the transcript events (`session.input_transcript.delta`, same page group): either is a redesign of that part, not a carry-over.
- **Platform-spoken lines:** the lines our server speaks itself (read-back, keypad prompts, confirmations) are SignalWire `<Say>`/`<Gather>` steps outside the model session, so they do not depend on the model. What we inject into the model afterwards (today `conversation.item.create` with a system message) has GPT-Live equivalents: `session.instructions.append`, `session.thinking.append` (facts, not said at once) and `session.commentary.append` (said aloud, may be paraphrased), each up to 500 tokens (https://developers.openai.com/api/docs/guides/live-conversations). Greeting, resume and tool-wait "filler" lines (`VoiceScripts`, response-level `instructions` in Realtime) behave differently: for exact wording OpenAI says to play "a verified recording or rendered clip through your application", and GPT-Live keeps talking while the backend works, with a section on suppressing automatic acknowledgments (https://developers.openai.com/api/docs/guides/live-conversations , https://developers.openai.com/api/docs/guides/live-delegation). Our exact-wording lines must be re-tested.

## 7. Zero data retention and data use

- Both endpoints: "Data used for training: No"; abuse-monitoring logs kept 30 days by default; Zero Data Retention and Modified Abuse Monitoring need OpenAI's approval and are set per organisation or project (https://developers.openai.com/api/docs/guides/your-data).
- `/v1/realtime`: application state "None"; Zero Data Retention eligible "Yes" (same page). `/v1/live/sessions`: application state "None, or 30 days if stored"; eligible "Yes, with limitations": with ZDR `store` is treated as false, and stored recordings, downloads and forking are not available; session storage is off by default (https://developers.openai.com/api/docs/guides/data-residency). Data residency: United States and Europe; "Delegated backend models and tools have their own data controls" (same page). Creating a custom voice through `/v1/audio/voices` is not compatible with ZDR (https://developers.openai.com/api/docs/guides/custom-voices).
- Our own rules do not change: we store no audio or transcript (`docs/VOICE.md` section 3); with GPT-Live the transcript events pass through us the same way. ZDR still has to be requested from OpenAI before real customers call (VOICE.md, owner action).

## 8. Deprecation outlook for the Realtime API

- The deprecations page lists **no shutdown for the `/v1/realtime` endpoint and none for `gpt-realtime-2.1` or `gpt-realtime-2.1-mini`**; they are named as the replacements. Older ids are deprecated: `gpt-realtime` and `gpt-realtime-2025-08-28`, `gpt-4o-realtime` (replacement `gpt-realtime-2.1`) and `gpt-realtime-mini`, `gpt-4o-mini-realtime` (replacement `gpt-realtime-2.1-mini`), shutdown **Jan 20, 2027** (https://developers.openai.com/api/docs/deprecations). Our configured ids are the current ones (`VoiceOptions.cs`).
- Direction: "For a new conversational voice application, start with GPT-Live", and "Use the Realtime API when you need its session and tool model" (https://developers.openai.com/api/docs/guides/audio). OpenAI publishes a "Migrate to GPT-Live" guide with a path "From Realtime API" (https://developers.openai.com/api/docs/guides/live-migration). **I found no announcement that Realtime will be retired**; its long-run status is OPEN beyond that.

## 9. Migration size

It is **not a drop-in swap but it can stay a connector behind the same phone-side code**: GPT-Live would be a second bridge class chosen per call, next to `RealtimeBridge`.

Stays as is: the SignalWire side (Stream relay, `VoicePlayback` marks and clear, `<Say>`/`<Gather>`/`<Pay>` steps, SMS, PIN, cart and order logic, `VoiceCallState`), because the model is behind `RealtimeBridge` only (`Voice/RealtimeBridge.cs` is the only file with Realtime events, plus `VoiceEndpoints.cs` that starts it and `Program.cs` that registers it).

Changes or is added:
1. a new bridge (about the size of `RealtimeBridge.cs`, 313 lines): `session.start` with model, short instructions, `audio/pcmu` 8 kHz, voice, delegation configuration; `session.input_audio.append` / `session.output_audio.delta` instead of the Realtime events; no `response.done` / `response.created` lifecycle;
2. tool path: function tools move to the delegation backend (Responses or client delegation), including the `off_topic` tool; instructions split into two prompts (`VoiceTools.cs`, `VoiceTopic.cs`, the instructions and `VoiceScripts`);
3. cost tracking: today tokens are read from `response.done` and priced per million (`VoiceCallStore.AddUsageAsync`, `VoiceReport.cs`, `VoiceOptions` prices); GPT-Live bills duration, final usage arrives in `session.closed` ("Voice-duration updates are cumulative snapshots; do not add them together", https://developers.openai.com/api/docs/guides/voice-websockets), plus the backend's own usage;
4. options and report: a new `Voice:ModelMode` value or a new setting to pick the engine, `Voice:TurnDetection` not applicable, per-minute price option; the staff report's tiers;
5. tests: the scripted voice tests use a fake Realtime server (`FakeRealtime`, used directly by 15 test files and, through `VoiceScenario`, 31): a fake GPT-Live server and a second set of barge-in, tool and cost tests;
6. docs: `docs/VOICE.md`, decisions.

## 10. Recommendation (for Ronald; the decision is his)

**Recommendation: stay on Realtime for the phone line now, and run a bounded GPT-Live trial behind the existing A/B mechanism only if Ronald wants to find out whether it sounds better.**

Why stay: (a) nothing in OpenAI's documentation says Realtime is going away, and our ids are the current ones; (b) our barge-in (V-12), tool, off-topic and cost-tracking design maps directly to Realtime and is tested, while GPT-Live moves tools into a backend and has no documented turn-detection or truncate controls, which are the parts that matter most on a phone line (sections 4 to 6); (c) GPT-Live is not cheaper than our `mini` tier and the backend comes on top (section 1); (d) SignalWire is not a documented GPT-Live route, so we would run the bridge ourselves either way (section 3).

Why a trial could still be worth it: OpenAI points new voice applications to GPT-Live and describes it as more natural with smoother interruption handling (sections 2 and 8). The way to learn is a measured A/B: a second bridge selected per call by the same kind of split as `Voice:ModelMode`/`Voice:MiniPercent`, a small share of calls, comparing audible latency, interruptions, task completion and cost on our own calls.

What would settle the OPEN points first (a half-day spike with a test project, no callers): can GPT-Live take SignalWire's `pcmu` 8 kHz stream, how it behaves when the phone queue is flushed with `clear`, whether any turn-taking control exists, whether `cedar` or another voice we like exists, WebSocket session-start billing, and measured latency.
